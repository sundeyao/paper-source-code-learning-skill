# Skill 行为测试用例

这些是人工验收用例，不是自动化模型评测。每个用例都应在真实代码仓库中执行，并检查 Codex 回答是否符合预期。

## 测试 1：新仓库整体架构

**提示词**

> 使用 `$paper-source-code-learning`。先检查当前仓库和配置，告诉我模型整体执行流程、入口函数、主要模块与关键张量。先不要展开每个模块内部的全部细节。

**预期行为**
- 先检查当前工作区和配置。
- 说明实际仓库/版本线索。
- 给出由源码支持的端到端流程。
- 对未确认的模块明确标注，不臆造调用顺序。

## 测试 2：张量形状

**提示词**

> 这个 `[B,S,C]` 张量是在哪里生成的？请找到真实代码，解释 B、S、C 在当前模型中的含义，以及上一步和下一步的形状变化。

**预期行为**
- 搜索变量定义与调用位置。
- 以当前实现解释每个维度，不把 C 自动当作通道数或类别数。
- 展示具体运算与前后形状。
- 给出文件路径和函数名。

## 测试 3：Top-K 语义

**提示词**

> 这个模型有两个 Top-K。请分别找到它们在源码中的位置，说明各自的输入、排序对象、axis、K 值、索引含义，以及它们是否保证框不重复。

**预期行为**
- 分开定位每个 Top-K，而不是只按流程图推断。
- 说明是否在 Top-K 前做了 max、flatten、sigmoid/softmax。
- 解释索引怎样还原并映射到类别或框。
- 不把 Top-K、NMS 和框合并混为一谈。

## 测试 4：匈牙利匹配

**提示词**

> 匈牙利匹配在这个项目中发生在模型的哪个位置？请追踪 matcher 的调用者、cost matrix、返回索引和 loss 的关系，并区分训练与推理。

**预期行为**
- 找到 matcher 的真实实现与调用点。
- 如果当前仓库/路径没有使用 Hungarian matching，明确说明检查范围并继续搜索相关 Criterion/训练代码。
- 不把它说成推理后处理。

## 测试 5：检查不存在或未确认的功能

**提示词**

> 这个模型的后处理会把多个框合并成一个题目区域吗？请以源码为证据回答。

**预期行为**
- 搜索后处理和部署流水线的真实代码。
- 区分 NMS、包含关系过滤、框坐标合并、图像裁剪。
- 如果只检查了部分文件，说明范围；没有证据时不声称存在。

## 测试 6：任务迁移

**提示词**

> 我想把这个模型迁移到学生试卷上的题目和手写作答区域检测。请先对比原模型类别、标注粒度、数据分布、预测头、loss、matcher 和后处理，再给出最小实验方案。

**预期行为**
- 先检查模型配置和类别映射。
- 不直接建议重写网络。
- 区分必须修改、建议实验和暂时保留的模块。
- 给出数据与验证要求。

## 团队验收评分

每项按 0–2 分评分：0 = 没做到或不可靠；1 = 部分做到但缺少证据/形状/阶段区分；2 = 明确、可核验且与当前实现一致。

| 维度 | 分数 |
|---|---:|
| 检查当前源码与配置 | /2 |
| 调用链与文件位置 | /2 |
| 张量形状和实际运算 | /2 |
| 训练/推理/后处理区分 | /2 |
| 不编造缺失实现 | /2 |
| 总分 | /10 |

建议每个关键用例至少 8/10；任何虚构源码事实或混用版本都应作为阻断问题修复。

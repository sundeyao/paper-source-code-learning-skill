# 模型迁移与改造评估

## 目标
根据原模型真实实现判断它与新任务的差异，并提出可验证的最小改造方案。

## 1. 明确预测对象
先定义每个检测/分类/分割实例具体代表什么：整篇文档、题目、小题、文字行、手写答案还是填空框？多个实例是否允许重叠？是否需要阅读顺序、实例 Mask 或 OCR/VLM 下游处理？标注边界和包含关系规则是什么？

目标定义不清时，先问一个能改变技术方案的问题。

## 2. 对比原任务和新任务
| 维度 | 需要核查的问题 |
|---|---|
| 类别 | 原类别数、类别语义、标签 ID 与新任务是否一致？ |
| 图像分布 | 扫描/拍照、印刷/手写、倾斜、阴影、噪声是否变化？ |
| 粒度 | 原模型检测的对象与新任务要求的对象是否同一级别？ |
| 标注 | 框、Mask、阅读顺序、文本转录分别需要什么标注？ |
| 输出 | 新任务需要类别、坐标、Mask、顺序还是识别文本？ |
| 评估 | 使用哪些指标与错误案例？ |

## 3. 判断改动层级
逐项检查 Backbone 预训练权重、Encoder/特征融合、Query 初始化、Decoder、分类头、框回归头、损失、Matcher/Assigner、Mask/阅读顺序分支和后处理。

将建议分成：
- **必须修改**：原实现与新任务接口或标签定义不兼容；
- **建议优先实验**：可能有帮助，但需验证；
- **暂不修改**：先建立基线，避免没有证据地改结构。

## 4. 建议最小实验顺序
1. 固定数据划分和标注规范。
2. 用小规模样本验证数据管线与标签映射。
3. 运行原模型建立基线并保存失败案例。
4. 调整必要的类别配置/预测头并微调。
5. 按验证集分析漏检、误检、定位偏差、重叠和跨类别混淆。
6. 只有错误分析支持时，再尝试改变 Decoder、损失、匹配或后处理。
7. 记录每次实验的配置、数据版本、指标和可复现步骤。

不要把“能运行”视为“适合任务”，也不要把“类别名称不匹配”自动等同于必须重写整个网络。

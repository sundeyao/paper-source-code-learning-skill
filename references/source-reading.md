# 源码阅读与调用链追踪

## 目标
把论文概念映射到当前仓库的真实实现，确认实际调用顺序，而不只是列举模块。

## 1. 确认版本与入口
记录仓库路径、分支/提交（若可获取）、框架及版本、配置文件、推理入口、训练入口、模型构建入口和关键类。优先从用户提到的函数或变量反向定位调用者，再顺着调用向下追踪。

## 2. 画出最小端到端流程
```text
输入 → 预处理 → Backbone → 特征融合/Encoder → 候选生成
     → Decoder/Prediction Heads → 后处理 → 最终输出
```
只把当前源码中已核实的模块放入图中。可选分支应标注触发条件。

## 3. 对每个关键函数做五项核验
| 核验项 | 要回答的问题 |
|---|---|
| 调用关系 | 谁调用它？它调用谁？ |
| 输入 | 实际传入哪些变量和配置？ |
| 运算 | 代码逐步执行什么操作？ |
| 输出 | 返回哪些张量、结构或副作用？ |
| 下游 | 输出被谁消费？ |

如果有多个同名实现，追踪当前模型构建路径实际使用哪一个。

## 4. 证据等级
- **源码已确认**：已检查实现代码和相关调用点。
- **论文说明**：论文明确描述，但当前源码未能确认。
- **推断/待验证**：基于现有证据提出解释，需要更多代码或实验验证。

不要把“搜索不到”直接升级为“整个系统没有”。说明搜索范围。

## 5. 避免常见错误
- 不把论文图中的模块自动视为当前代码路径的一部分。
- 不把另一个框架或分支中的实现套用到当前仓库。
- 不只凭函数名称推断行为；阅读运算语句和调用点。
- 不编造行号。无法获得行号时，给出文件路径和函数/类名。
- 若实现分散在模型、Criterion、Matcher、PostProcess 和部署流水线中，分别说明职责。
